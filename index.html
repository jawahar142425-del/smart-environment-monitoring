Smart Environmental Monitoring & Automated Alert System

Measure temperature, humidity, air quality and smoke, store the data in the cloud, predict pollution spikes with machine learning, and warn people automatically. This page documents Part 1, the sensing and data acquisition unit.

Part 1: Jawahar S25BIT0343Software and simulation only, no physical hardware

How the four parts connect

Each part hands its output to the next one. Part 1 produces the readings that every later part depends on.

Part 1: sensing and data acquisition

An ESP32 reads three sensors, converts the raw signals into meaningful units, labels the air quality, and publishes one JSON message every 5 seconds over MQTT.

Measure

DHT22 gives temperature and humidity. MQ135 gives a CO₂-equivalent value. MQ-2 gives a smoke value.

Calibrate

Each MQ sensor is calibrated in clean air to find its reference resistance R0, stored in flash memory.

Transmit

Readings leave the node as JSON on an MQTT topic, so Parts 2 to 4 can subscribe without knowing about the sensors.

How it runs without hardware

The whole node runs in the Wokwi online simulator. The simulator sketch prints exactly the same JSON as the full ESP32 firmware (which adds Wi-Fi, MQTT and clean-air calibration), so moving to hardware later needs wiring and calibration, and the other parts see the same data format.

A potentiometer is not a gas sensor, so in the simulator sketch its position is mapped straight to ppm: each quarter of the knob is one air quality level. On real hardware the MQ module outputs up to 5 V, a 10k and 20k divider brings it to 3.3 V for the ESP32, and the full firmware converts it with the resistance curves below.

For Part 3, tools/generate_sample_data.py produces longer datasets in the same format, including simulated smoke and ventilation events.

Calibration

MQ sensors change resistance with gas concentration. The firmware converts the analog voltage to a resistance (Rs), then to ppm using the ratio Rs/R0.

Vout = Vadc x 1.5                      undo the 10k/20k divider
Rs   = RL x (5 - Vout) / Vout          sensor resistance
MQ135 CO2 ppm = 116.6 x (Rs/R0)^-2.769
MQ-2 smoke ppm = 3.0e7 x (Rs/R0)^-8.308

R0 is found by sending c in the serial monitor while the sensors are in clean air. The firmware averages 50 samples and saves R0. For MQ135, clean air is taken as 420 ppm. For MQ-2, clean air is Rs/R0 = 9.83 from the datasheet.

These formulas and the clean-air calibration are used by the full firmware on real hardware. In the simulator, the knob is mapped directly: 0 to 25% GOOD, 25 to 50% MODERATE, 50 to 75% POOR, 75 to 100% HAZARDOUS. MQ values are estimates for trends and threshold alerts, not laboratory measurements.

Data format

Topic envmon/jawahar/node01/data, one message every 5 seconds:

{
  "device_id": "node01",
  "timestamp": "2026-10-10 10:00:05",
  "temperature_c": 29.9,
  "humidity_pct": 67.2,
  "mq135_co2_ppm": 442,
  "mq2_smoke_ppm": 3,
  "air_quality": "GOOD"
}

Topic envmon/jawahar/node01/status holds online or offline, set as the MQTT last-will message.

Limitations

The sensors are simulated, so the readings show that the data format, the air quality levels and the JSON output work, not how real gas sensors behave. Real MQ sensors also need a 24 to 48 hour burn-in and drift with temperature and humidity.
